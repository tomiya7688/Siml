# ポインタ仕様

状態: 最小実用版の草案として一部決定  
最終更新: 2026-10-28

この文書は、現在までに決めたSimlのポインタ規則を記録します。

ポインタとメモリの仕様全体はまだ未完成です。ここでは、すでに決めた部分だけを固定します。

## 基本構文

ポインタ型と基本操作は、OSコードを読みやすくするため、直観的で短い構文を使います。

```text
*T   // Tへのポインタ型
&x   // xのアドレスを得る
*p   // pが指す値を読む、または書き込み先として使う
```

低水準コードではこれらの操作が頻繁に現れるため、特別な関数呼び出しや長い構文にはしません。

## nullを特別扱いしない

Simlは `null` を言語組み込みの特別な値として持ちません。

また、アドレス0にも言語仕様上の特別な意味を与えません。

```text
0番地が使える環境      -> 通常のアドレスとして使える
0番地を無効とするOS    -> OS側の規約
0番地アクセスで例外が出るCPU -> CPU側の動作
```

0番地を指すポインタが必要な場合は、整数からポインタへの明示変換を使います。

明示的な型変換はすべて `式 as 型` に統一するため、例えば次のように書きます。

```text
0 as *u8
addr as *u32
p as usize
```

整数→ポインタ、ポインタ→整数だけのための専用構文や専用関数は作りません。

これにより、`null` 専用の字句、構文木要素、型規則、代入規則、参照時検査などを最小コンパイラへ追加しません。

## ポインタ演算

OSや低水準プログラムで直接必要になるため、Simlは限定的なポインタ演算を持ちます。

`p: *T` に対して、次の形だけを認めます。

```text
p + n
p - n
p1 - p2
```

この機能から、それ以外のポインタ算術は導入しません。

特に次はコンパイルエラーです。

```text
n + p       -> コンパイルエラー
p1 + p2     -> コンパイルエラー
p * n       -> コンパイルエラー
p / n       -> コンパイルエラー
```

有効な形を少数に限定することで、構文解析、型検査、仕様、低水準化を小さく保ちます。

## 要素単位の移動

`p + n` と `p - n` は、生のバイト数ではなく `T` の要素数だけ移動します。

概念上は次の意味です。

```text
p + n  -> address(p) + n * sizeof(T)
p - n  -> address(p) - n * sizeof(T)
```

例えば `p: *u32` で `u32` が4バイトなら:

```text
p + 1  -> p から4バイト先
p + 2  -> p から8バイト先
```

1バイト単位でアドレスを進めたい場合は `*u8` を使えます。

`n` に許す整数型はまだ未決定です。仕様とコンパイラが最も単純になるものを選びます。

## ポインタ同士の差

同じポインタ型どうしを引くと、バイト数ではなく要素数の差を返します。

`p1: *T` と `p2: *T` について、概念上は:

```text
p1 - p2 -> (address(p1) - address(p2)) / sizeof(T)
```

結果型は `isize` とします。

`*u32` の例:

```text
p1 = 0x1010
p2 = 0x1000

p1 - p2 -> 4
```

別々のメモリ領域を指すポインタ同士を引いた場合の扱いは、まだ未決定です。

## 配列からポインタへの暗黙変換はしない

配列値は暗黙にポインタへ変わりません。

Cの配列からポインタへの暗黙変換を持ち込まず、配列とポインタを別の概念として扱います。

配列の記憶領域を指すポインタを得る操作は明示的にします。

配列要素や配列全体のアドレスを取る具体的な構文は、まだ未決定です。

## ポインタと整数の暗黙変換はしない

ポインタ演算を導入しても、ポインタと整数の暗黙変換は認めません。

ポインタから整数、整数からポインタへの変換は、必ず明示的に `as` を使います。

```text
addr as *u32
p as usize
```

型変換構文は整数変換などと共通化し、ポインタ専用の変換構文は増やしません。

許可する変換の組み合わせと、各変換の正確な意味はまだ未決定です。

## 設計理由

カーネル、メモリ管理、ドライバ、バイナリデータ処理などに必要な操作を残しつつ、同等のCコンパイラより小さな規則で実装できることを狙います。

最初の仕様では、意図的に次を避けます。

- `integer + pointer` のような左右対称の別表記
- ポインタに対する任意の算術演算
- 配列からポインタへの暗黙変換
- ポインタと整数の暗黙変換
- ポインタ式に絡むC風の複雑な変換規則

今後決めるメモリ仕様も、隠れた変換やプログラム全体の解析より、局所的で明示的な規則を優先します。
